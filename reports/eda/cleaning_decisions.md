## How the numbers below were produced (read this first)

- **Full-data counts** (rows containing a pattern) come from DuckDB queries over the six `data/interim/*.parquet` files. They cover every row.
- **"Lift" numbers** come from a throw-away prototype run on the existing deterministic ~0.5% positive-pair sample (`reports/eda/positive_pair_sample_s2.csv` / `_s3.csv`; 7,361 / 11,015 / 7,928 / 11,803 pairs for S2-India / S2-US / S3-India / S3-US). They measure **how many TRUE links become exactly equal** after one rule is applied on its own. They say nothing about false candidates (precision), and the sample is exploratory, not a validation fold. Every rule below must be re-measured on the frozen development fold with collision counts (Phase 8 of the plan) before it is promoted.
- Name-lift denominators are pairs whose target name is Latin-script only; address-lift denominators are pairs with a non-empty target address.
- Example IDs come from the samples and queries above. Train-set IDs have labels; test-set IDs are marked *(test)* and are text-only examples.

## Things measured that did **not** help (kept so nobody repeats them)

- NFKC compatibility view: identical to the v1 key in every row (N-20).
- `anyascii_n` (anusvara -> n) once the coarse skeleton is used: identical results to plain `anyascii`; it only helps the base skeleton.
- `indic-transliteration` (ITRANS/HK/IAST) instead of `anyascii`: same accuracy after the coarse skeleton (HK slightly worse), 8-15x slower, extra dependency.
- Dropping bracket text from `name_core`: -1.4 to -1.5 points in the US, +0.3 in India S2 (X1 in `name_pair_agreement.md`).
- Any single-pass skeleton: not a normal form (vowel removal creates new doubles and digraphs); fixed a property-test failure.

- Address rules measured in Phase 5 that were **not shipped or gave nothing** (true-pair sample, exact token-set agreement):
  - `n` as a number label next to `no`: identical to 0.01 pp; it also deletes real unit letters, so only `no` is a label.
  - A label separated from its number by a comma (A-14): 0.0 pp; shipped only for consistency and the fixed-point property.
  - Keeping number labels instead of dropping them: -0.9 pp (S2-India), -1.1 pp (S3-India), 0 in the US.
  - `sq` -> `square` and other US street abbreviations below the evidence threshold: not written (`sq` has 2,793 multi-token segments).
  - **Candidate for `feat_v2_1`, not shipped**: dropping a trailing `city`, `county` or `township` from US segments (S2/S3 append `CITY` to 1.4 pp more rows than S1, drop `COUNTY` from 1.3 pp, add `Township` to 0.8 pp): +1.2 pp (city alone) to **+1.8 pp (all three)** in S2-US and +1.7 pp in S3-US. It is a segment-level rule that makes `address_canon` non-idempotent for cities named like a state (`Oklahoma City` as the last segment) and needs a guard for state-name remainders (`Kansas City` -> `Kansas`), so it should be added together with B's ablation, not silently.
  - Glued labels (`NO119`): 0.5% of S1 rows vs 0.4% of S2/S3, natural variety, not fixed.
- Removing mojibake/control characters: 0 pp on exact address agreement.
- Accent folding on addresses: 0 pp (address accent noise is rare).
- Apostrophe joining on Latin India/US names: 0 pp (few apostrophes); revisit for French with B.
- Dropping bracket text on its own: negative (N-07).
- `indic-transliteration` (ITRANS) vs `anyascii` for name-level matching: `anyascii` was better out of the box (whole-name skeleton ratio >= 80: 82% vs 74%); the ITRANS output keeps inherent schwa vowels (`smArTa`).
